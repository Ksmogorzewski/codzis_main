# Znajomi — plan wykonania

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** dodawanie znajomych kodem/QR z akceptacją i widok wydarzeń, na które idą znajomi (zakładka „Znajomi” zamiast Eksploruj, „Ola idzie” na kartach).

**Architecture:** nowa tabela `codzis-friends` (jeden zapisujący: client-api) w modelu jednej tabeli bez GSI; nowy moduł `src/client_api/friends.py` (logika + DynamoDB), cienkie trasy w `handler.py`. Front: trasy `/znajomi` i `/znajomi/dodaj/$code`, hooki Query, QR generowany w przeglądarce, mapa „wydarzenie → imiona znajomych” doklejana po stronie klienta do wszystkich list.

**Tech Stack:** Python 3.13 + boto3 (Lambda zip, bez nowych zależności), pytest + moto; React 19 + TanStack Router/Query + Zod + Tailwind 4/shadcn, vitest; Terraform (AWS provider 6).

**Spec:** `docs/superpowers/specs/2026-10-18-znajomi-design.md` (czytać razem z tym planem).

## Global Constraints
- Gałąź `feat/znajomi` (na `feat/twoje-wydarzenia`). Nie pushować, nie mergować, nie robić `terraform apply`, nie pisać do AWS. W root `AGENTS.md` jest cudza niezacommitowana zmiana — nie stage'ować (tylko własne hunki przez `git add -p`, najlepiej nie ruszać).
- Commity po polsku (`feat(api): …`, `feat(portal): …`, `feat(seed): …`, `test(…)`), zakończone pustą linią i `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Nigdy `git add -A`.
- **Bez akceptacji nikt nie widzi moich zapisów.** Nigdy e-maili — tylko imię. Znajomi widzą tylko nadchodzące zapisy.
- Limit **50 znajomych**. Limit **10 błędnych kodów na godzinę** na użytkownika → `429` z komunikatem „Za dużo prób. Spróbuj za godzinę.”.
- Kod: `WAW-` + 6 znaków z alfabetu `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (bez 0/O/1/I), losowany `secrets.choice`. Wejście normalizowane: wielkie litery, bez spacji/myślników, prefiks `WAW` opcjonalny.
- Konto bez imienia: każda akcja znajomych (pokazanie kodu, zaproszenie, akceptacja) → `409 {"code": "name_required"}`. Front prosi o imię od razu po zalogowaniu (istniejący `NameDialog`).
- Rekomendera (`src/recommender_api/`, `recommender/`) nie ruszamy. Jedna mała zależność frontu do QR (bez własnych zależności); skanera w aplikacji nie budujemy.
- Teksty UI po polsku; zasady wyglądu z `src/frontend/AGENTS.md` („bez AI slop”, jasny/ciemny, ≥44 px, telefon 360 px bez poziomego przewijania).

## Review Focus
1. Kod wpisany „byle jak” (`waw 7k2p9x`, `7K2P9X`, `WAW-7K2P9X `) — działa jak poprawny. → Task 1 `test_normalize_code_variants`.
2. Link z QR otwarty przez niezalogowaną osobę — po zalogowaniu wraca na ekran zaproszenia. → Task 4 `invite route keeps code through login redirect`.
3. Zaproszenie do kogoś, kto już jest znajomym, ma moje oczekujące zaproszenie albo sam mnie zaprosił — bez duplikatów, w ostatnim przypadku automatyczna akceptacja. → Task 1 `test_invite_existing_states`.
4. Usunięty znajomy — jego wydarzenia znikają z „Znajomi idą” i z kart bez odświeżania strony (unieważnienie zapytań). → Task 4 `remove friend invalidates going`.
5. 51. znajomy i 11. zły kod — czytelny błąd, bez częściowego zapisu. → Task 1 `test_friend_limit` i `test_rate_limit_wrong_codes`.

### Task 1: Backend — model znajomych (moduł `friends.py`)

**Files:**
- Create: `src/client_api/friends.py`
- Test: `tests/client_api/test_friends.py`; Modify: `tests/client_api/conftest.py` (tabela `test-friends`, env `FRIENDS_TABLE`)

**Interfaces:**
- Consumes: `codzis_common.http.ApiError`; env `FRIENDS_TABLE`.
- Produces (używa Task 2):
  - `normalize_code(raw: str) -> str | None` (zwraca `WAW-XXXXXX` albo `None`)
  - `get_or_create_code(user_id: str) -> str`, `regenerate_code(user_id: str) -> str`
  - `preview(user_id: str, code: str, now: int) -> dict` → `{"userId", "name"}` (liczy się do limitu złych prób)
  - `invite(user_id: str, name: str, code: str, now: int) -> dict` → `{"status": "pending" | "friends", "userId", "name"}`
  - `accept(user_id: str, name: str, from_id: str, now: int) -> dict` → `{"status": "friends"}`
  - `decline(user_id: str, from_id: str) -> None`, `remove(user_id: str, friend_id: str) -> None`
  - `overview(user_id: str) -> dict` → `{"code", "friends": [{"userId","name","since"}], "incoming": [...], "outgoing": [...]}` (`incoming/outgoing`: `{"userId","name","createdAt"}`)
  - `friend_ids(user_id: str) -> dict[str, str]` (id → imię)

**Model (jedna tabela, PK `userId`, SK `sk`, TTL `expiresAt` w sekundach):**
| `userId` | `sk` | pola |
|---|---|---|
| `<sub>` | `code` | `code` |
| `code#WAW-XXXXXX` | `owner` | `owner` (sub), `ownerName` |
| `<sub>` | `friend#<other>` | `name` (imię drugiej osoby), `since` |
| `<sub>` | `in#<from>` | `name`, `createdAt`, `expiresAt` (+30 dni) |
| `<sub>` | `out#<to>` | `name`, `createdAt`, `expiresAt` (+30 dni) |
| `<sub>` | `limit` | `attempts` (licznik `ADD`), `expiresAt` (+1 h) |

Zapisy wielorekordowe przez `TransactWriteItems` (zaproszenie: `out` + `in`; akceptacja: usuń `in`/`out`, dodaj dwa `friend#`; usunięcie: dwa `Delete`; nowy kod: usuń stary `code#…`, dodaj nowy z `attribute_not_exists(userId)` i ponów przy kolizji).
